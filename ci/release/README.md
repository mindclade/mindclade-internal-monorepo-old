# Reviewed release requests

Production artifact authority starts with a pull request that adds exactly one
`ci/release/requests/vX.Y.Z.yaml` file. The file is immutable after merge and selects one name
from `targets.yaml`; it cannot supply commands, registry paths, identities, or signing roots.

The `release.yml` push event is GitHub-platform-authenticated and restricted to protected
`main`. It discovers one newly added request, validates it before WIF authentication, and then
runs the ARC canary, build, independent qualification, protected deployment attestation, and
review-only GitOps promotion proposal. There is no `workflow_dispatch`, tag, API dispatch, or
caller-selected SHA authority path.

`ci/release/requests/` is therefore armed, not illustrative. A merged file there *is* the
trigger; it is not a place to park a worked example. The example below and the cases in
`tests/test_release_request.py` are how a request shape is demonstrated without starting a
release.

Validation resolves each catalog entry's Bazel labels to a package in the checked-out tree
during that credential-free discovery step. Label syntax is not label existence, and before
this the first thing to notice a renamed or deleted package was `bazel build` inside the
credentialed build job — a stale entry surfaced mid-release instead of as a red check.

Version `v1beta2` intentionally permits one target per request and makes rollback strategy
explicit. Target catalog schema 2 binds
that name to a release kind, GitOps application, rollout class, named image build/push targets,
typed non-image artifact slots, and fixed qualification targets. GitHub reusable-workflow outputs
remain singular; use separate release IDs for independently promotable subjects.

The closed catalog includes `protobuf-contracts`, a data-only OCI subject
containing the canonical sources, transitive descriptor set, compatibility
baseline, and machine-readable maturity/RPC policy. Its qualification targets
compile every Go projection, link a real generated-code consumer, and verify
the TypeScript and descriptor surfaces before the generic release workflow can
attest or propose promotion.

## Which components a target releases

The reference points from `components.toml` to this catalog — a component carries
`release_target = "<catalog name>"`, and a catalog entry carries no component field. Three
reasons, and they are worth stating because the opposite direction looks equally natural:

* `tools/analysis/check_component_maturity.py` evaluates `requires_release_target` per
  component, so the component record is where the gate reads. A `component:` field here would
  need a reverse index that checker does not build.
* One subject releases many components. `protobuf-contracts` ships all ten
  `protocols.protobuf.*.v1` packages as a single digest-addressed bundle — a scalar field here
  could not say that, and a list would restate what ten component records already say.
* This file sits under the `release-authority-paths` ruleset and needs platform *and* security
  review. Renaming a component should not require a security review of the file that names
  registries, attestors, and push targets. The catalog declares release mechanics; the
  component record declares everything else about a component.

Declaring a release target satisfies exactly one of the six `production` gates in
`maturity.toml` — the others are tests, qualification, an SLO, a runbook, and a build target.
A component with a release target is a component whose release vehicle is known, not a
component that is ready to ship.

Coverage is currently partial and the gaps are not oversights:

* `protobuf-contracts` maps cleanly onto the ten `protocols.protobuf.*.v1` components. Its
  layer is built from `//protocols:all_proto_sources` and `:protobuf_descriptor_set`, which
  enumerate exactly those ten packages.
* `go-vanity` releases `services/go_vanity`, which the `services.go_vanity` component now
  declares with `release_target = "go-vanity"`. It is recorded at `implemented`, where the
  field is optional; `requires_release_target` is one of the six gates `production` demands,
  so the declaration says the release vehicle is known, not that the component is ready or
  that anything has shipped.
* `weights-fixture` releases a synthetic bundle generated by `make_fixture.py` so the weights
  distribution path can be exercised before a real checkpoint exists. It is not the artifact
  of the `models.reference_affine` component that happens to contain its directory, and
  attaching it there would claim a release vehicle for a model the fixture does not carry.
  Its `qualificationMode: build` over its own `buildTarget` is a rebuild, not independent
  evidence — the honest reading is that this entry proves packaging, not the artifact.

An ordinary request names the exact previous release ID and subject digest. The pair is rollback
lineage, not merely an image hint, and cannot be replaced with a mutable tag or a zero digest.
The first `v1.0.0` request instead uses `bootstrap`; rollback then removes the development
selection and restores the fail-closed digest-zero state. Bootstrap is rejected for every other
release.

Example:

```yaml
---
apiVersion: release.mindclade.dev/v1beta2
kind: ReleaseRequest
metadata:
  name: v0.2.0
  changeTicket: PLATFORM-1234
spec:
  target: go-vanity
  rollback:
    strategy: previous-release
    previousRelease:
      id: v0.1.0
      subjectDigest: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

Validate without credentials. Rehearse the request *before* adding it to `requests/`, because
adding it there is the trigger — the form below takes the draft from wherever you are keeping
it and applies every rule the merged file will face:

```sh
python3 ci/release/release_request.py validate \
  --request /path/to/draft/v0.2.0.yaml \
  --source-sha 0123456789abcdef0123456789abcdef01234567 \
  --rehearsal
```

`--rehearsal` relaxes the directory requirement and nothing else: catalog membership, rollback
lineage, label resolution, and the filename/`metadata.name` agreement are all still enforced,
so a request that rehearses clean passes for the same reasons once committed. It is accepted
only by `validate`. `inspect` and `build` — the two the workflow actually calls — reject the
flag, so a rehearsal can never become the file a release acts on.

Once the file is in `requests/`, the same check without the flag is what CI runs:

```sh
python3 ci/release/release_request.py validate \
  --request ci/release/requests/v0.2.0.yaml \
  --source-sha 0123456789abcdef0123456789abcdef01234567
```

The producer bundle binds exactly six typed records: SBOM, provenance, vulnerability scan,
third-party notices, qualification, and rollback — the count `validate_qualification` enforces.
Adding a request does not make the source-only rollout active.
Production activation requires the reviewed `.github` v5 release, exact runner-group policy,
capability-specific WIF, connected ARC canary evidence, and a ready GitOps receiver.
